Neulight OMS Archive Layer 2

How the Archive Google Sheet is copied into Supabase, how to run it, and how to keep it working when the sheet changes.

Overview

The Neulight OMS runs on Google Sheets. Old records are moved out of the operational sheets into the Neulight OMS Archive spreadsheet by an existing process (Archive Engine #1). Google Sheets has a 10 million cell limit, so the Archive sheet can't keep everything forever.

This project (Archive Engine #2) copies the Archive sheet into a Supabase PostgreSQL database, which becomes the permanent, searchable history. The Archive sheet becomes a waiting area: rows sit there until they are copied, and the existing process can clean the sheet afterwards.

  • The transfer only reads the Archive sheet. It never edits or deletes cells.
  • It can be run as many times as needed. Rows already stored are skipped, never duplicated.
  • If a stored row's values change in the sheet, the archive keeps the stored version and logs the difference for review. Nothing is silently overwritten.
  • Every run is logged with counts of rows read, inserted, skipped, changed and failed.

The first arrow is Archive Engine #1, which already exists and is not part of this project. The second arrow is this project:

  1. Apps Script in the Archive spreadsheet reads one tab at a time.
  2. It maps each header to a table column, converts values, and sends rows in batches of 150.
  3. A Supabase function checks each row: insert if new, skip if identical, log if different, record a failure if invalid.
  4. The run is logged in archive_sync_log and archive_sync_control.

Why it's built this way

ChoiceReason
Google Apps ScriptRuns inside the spreadsheet the client already uses. No server, no extra cost.
Private archive schemaNot reachable through Supabase's public API. Only the secret service_role key can write.
Checks run inside SupabaseThe rules (types, IDs, insert/skip/change) live in one place. The script stays simple.
One table per sheet, same column namesThe first goal is to preserve history faithfully. Reshaping data for reports can come later.
No foreign keys between tablesOld history arrives in any order and may reference rows that were cleaned up. Links are checked and reported, not enforced.

First-time setup

A. Supabase

  1. Open the project → SQL Editor → New query.
  2. Paste and run 20261007000000_archive_schema.sql. If the RLS warning appears, choose Run and enable RLS. already done
  3. New query: paste and run 20261012000000_archive_transfer_rpc.sql.
  4. New query: paste and run 20261012010000_archive_maintenance.sql.
  5. Check: Table Editor → schema dropdown → archive. You should see the empty tables and archive_sync_control with 40 rows.

B. Keys

Go to Project Settings → API (or API Keys) and note:

ValueLooks like
Project URLhttps://xxxxxxxx.supabase.co
service_role key (may be under "Legacy API keys")A long string starting with eyJ
The service_role key can read and write everything. Never put it in a sheet cell, chat or email. The anon/publishable key will not work, on purpose.

C. Google Sheet

  1. Open the live Neulight OMS Archive Google Sheet (not an xlsx copy).
  2. Extensions → Apps Script. Replace Code.gs with the contents of apps-script/ArchiveTransfer.gs. Save.
  3. Gear icon (Project Settings) → Time zone → (GMT+08:00) Manila.
  4. On the same page, Script properties: add SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY. Save. Do not put the key in a cell or in the script file.
  5. Close the Apps Script tab. Reload the spreadsheet. An Archive menu appears.
  6. Archive → Test connection. Approve Google's permission prompt (Advanced → Go to … → Allow). You should see "Connected" and the list of enabled sheets.

Recommended first run

  1. Dry run products. Expect about 134 read, 134 inserted, 0 failed. (In a dry run, "inserted" means "would insert".)
  2. Transfer products. Then check Table Editor → archive.products.
  3. Transfer products again. Expect 0 inserted, 134 skipped. This proves reruns are safe.
  4. For another tab (for example orders): Dry run one sheet…, then Transfer one sheet….
  5. Transfer all enabled sheets. Repeat until every sheet reports SUCCESS.

How rows are matched

Each sheet has an ID rule in archive_sync_control (key_mode and key_columns). For each row coming from the sheet:

SituationResultStored row
ID not stored yetinsertedCreated
ID stored, same valuesskippedUnchanged; _last_seen_at updated
ID stored, different valueschangedUnchanged; sheet version saved in archive_row_changes
ID blank, duplicate in batch, or value doesn't fit the columnfailedNothing saved; reason in archive_row_failures

ID rules

key_modeHow a row is identifiedUsed by
pkOne ID columnMost sheets
composite2–3 columns togetherpromo_pack_components, api_tokens
walletwallet_txn_id when filled; otherwise the row's contentwallet_transactions (about 2,000 rows have no ID)
hashThe row's content only. An edited row becomes a new row.missing_data, dashboard sheets

The fingerprint

Every stored row has _row_hash: a SHA-256 of its non-blank values after conversion. Comparing fingerprints is how "same" and "different" are decided. Because blank cells are left out, adding an empty column to a sheet doesn't make stored rows look changed.

How values are converted

Column typeTaken fromRule
text (IDs, codes, names)What the cell displaysLong numeric IDs stored as numbers in Sheets are rounded by Google; the displayed text is the closest to the original
numeric(18,4) money, quantitiesThe cell's stored numberNot the formatted display, so currency signs or decimal formatting can't change the value. Text cells are stripped to digits, . and -
integerThe cell's stored numberDecimals are cut off
timestamptz datesDate cellsRead as Philippine time (UTC+8) and stored as an exact moment
booleanCheckbox or textTRUE/FALSE, Y/N, yes/no, 1/0, t/f. Anything else fails the row
jsonbCell textParsed as JSON; invalid JSON fails the row
packing_duration_secondsNumber or timeTimes like 0:01:07 become seconds (67)
  • Blank cells become NULL, never an empty string.
  • Blank rows are skipped.
  • Header renames come from archive_header_map. Current: BRAND → brand, P60 days → p60_days, Emoji → emoji.
  • Unnamed columns: the two blank headers in wallet_transactions go to unnamed_col_ab and unnamed_col_ac.
  • Secrets: access_token, refresh_token, app_key, app_secret, shop_cipher and main_account_id are dropped before anything is sent.

Checking results

Run these in Supabase SQL Editor.

Status per sheet

select source_table, enabled, last_status, last_run_datetime,
       rows_read, rows_inserted, rows_skipped, rows_changed, rows_failed, last_error
from archive.archive_sync_control
order by load_order;

Recent runs

select execution_id, source_table, run_mode, status, started_at, duration_seconds,
       rows_read, rows_inserted, rows_skipped, rows_changed, rows_failed, error_message
from archive.archive_sync_log
order by started_at desc
limit 30;

Failed rows

select source_table, source_row_number, row_key, failure_reason, detected_at
from archive.archive_row_failures
order by detected_at desc
limit 50;

Changes waiting for review

select source_table, count(*) as pending
from archive.archive_row_changes
where resolution = 'PENDING' and applied_at is null
group by source_table;

Stored row count vs sheet

select 'orders' as sheet, count(*) from archive.orders
union all select 'order_lines', count(*) from archive.order_lines
union all select 'wallet_transactions', count(*) from archive.wallet_transactions;

Stored counts can be higher than the sheet once the archive process has cleaned old rows from the sheet. That's expected: the archive keeps them.

Maintenance

Full step-by-step instructions are in docs/MAINTENANCE.md. Summary:

The script reads columns and the header map from Supabase on every run. Most changes happen in Supabase only. Always dry run the affected sheet afterwards, and save your SQL as a new file in supabase/migrations/.

Column added, to archivealter table … add column (+ header map if the name differs)Nothing
Column added, not wantedHeader map row with target_column = nullNothing
Column removedNothing. Never drop the column. Accept + apply the resulting changesNothing
Column type changedFix the cell, or widen the type (usually to text)Nothing
New tabCreate table → prepare_archive_table → register in archive_sync_controlNothing
Tab renamedRename it back, or update source_table in the registry and header mapNothing
Tab deletedSet enabled = false. Never drop the tableNothing
Unnamed wallet columns get namesMap the names to unnamed_col_ab / unnamed_col_acNothing
New sensitive columnHeader map row with target_column = nullNothing
Header renamed

values ('orders', 'Order Date', 'order_date', 'Renamed in sheet');
Column added 
alter table archive.orders add column delivery_partner text;

-- only if the header isn't exactly the column name
insert into archive.archive_header_map (source_table, source_header, target_column)
values ('orders', 'Delivery Partner', 'delivery_partner');

Stored rows whose new cell is blank are skipped. Rows whose new cell has a value are logged as changed. Accept and apply them to copy the values in.

Ignore a column 
insert into archive.archive_header_map (source_table, source_header, target_column, note)
values ('orders', 'temp_calc', null, 'Helper column, not archived');
New tab 
create table archive.courier_rates (
  rate_id        text primary key,
  courier_code   text,
  rate           numeric(18,4),
  effective_date timestamptz
);

select archive.prepare_archive_table('courier_rates');

insert into archive.archive_sync_control
  (source_table, target_table, table_group, load_order, enabled, key_mode, key_columns)
values
  ('courier_rates', 'courier_rates', 'B', 21, true, 'pk', array['rate_id']);

For a sheet with no reliable ID, use archive_row_id bigint generated always as identity primary key, key_mode 'hash', key_columns array[]::text[], and add create unique index … on archive.<table> (_row_hash);

Accept and apply changes 
update archive.archive_row_changes
set resolution = 'ACCEPTED', resolved_at = now(), resolved_by = 'ethan'
where source_table = 'orders' and resolution = 'PENDING';

select archive.apply_accepted_changes('orders');

Applying copies sheet values into the stored row, never erases a stored value, never changes the ID, and refreshes the fingerprint so the next run skips the row.

Turn a sheet on or off 
update archive.archive_sync_control set enabled = true
where source_table = 'reservations_historical_recover';

Security

  • Schema archive is not exposed through the Supabase Data API. Row Level Security is on for every table with no policies, and the anon and authenticated roles have no access.
  • The script's functions can only be called with the service_role key.
  • The key is stored in Apps Script Script Properties, which aren't visible in the sheet. Anyone who can edit the script can read it, so limit editor access to the Archive spreadsheet.
  • If the key is exposed, rotate it in Supabase (Project Settings → API) and update SUPABASE_SERVICE_ROLE_KEY in Apps Script Project Settings → Script properties.
  • api_tokens secrets are never sent. The sheet is off by default; only metadata (platform, store, shop, expiry dates) is stored if enabled.
